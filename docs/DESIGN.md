# 中华航空 · 当前设计

## 产品与架构

本项目是航空版《中华铁路》式单机经营游戏：保留场景装载、真实客货、顺序选路、载具成长和到达结算的操作习惯，使用原创素材，不复制参考游戏的商标、图片、音效或代码。未取得原作证据的数值均明确作为航空化适配，不宣称完整一比一复刻。

`src/core` 是经营状态的唯一写入者，不依赖 DOM、React、PixiJS 或数据库。UI 只发送命令；机场、地图和飞机场景只读状态快照。到达、周转、补能、生产和前台经营都由时间事件结算，不使用动画回调，不允许重复结算。

## 新公司与首航教程

新游戏先通过“创建航空公司”选择公司名称与 Logo，确认并保存成功后进入机场目录；继续已创建公司不重复询问。名称去除首尾空白后为1–24个 Unicode 字符，拒绝控制字符；语言切换不翻译玩家名称。6款内置标志为机翼、朝阳、飞鸟、指南针、山峰和环球元素的原创航空风格 SVG，不使用现实航空公司的商标素材。左上角全局顶栏显示公司 Logo 与名称，长名省略并保留完整提示；公司等级、金币与机队控件保留，点券控件移除。

玩家可选择 PNG/JPEG/WebP 图片（非空、至多5 MiB、宽高均不超过4096像素），仅在本机解码、等比例居中缩放到128×128透明 PNG；不上传网络，不保存文件名、外部URL或临时 blob URL。存档 `company` 保存严格校验的 `name` 和 `logo`（预设 ID 或至多100,000字符的 PNG data URL），待创建新局为 `null`。PNG 校验尺寸、分块边界与校验和，导入时额外确认浏览器可解码。公司资料字段随当前v18存档保存；v16与其他版本拒绝、保留原数据、不自动迁移，数据库结构升级为2。

新建资料由核心 `found-company` 命令写入，不影响开局资金、机队、订单和教程。已创建公司不能重复创建覆盖名称；刷新、离线启动、导入导出和备份恢复均保留公司形象。开始界面提供“继续游戏”“新游戏”“载入存档”：继续最近游玩的公司，新游戏创建独立存档，载入存档展示公司名称、Logo、等级、资金、机队和保存时间。设置可保存并返回开始界面；取消创建或图片处理/持久化失败不改变原公司。

新局拥有北京1级基地、8,400金币和空机队，不再赠送初航机。上海需支付2,500金币解锁。空机队仅在尚未拥有过飞机的合法开局阶段有效；购机或组装后不得通过篡改存档清空所有飞机。

教程默认开启，运营教练林岚以原创半身像、宽对话框和可点击蒙版，引导玩家购买上海机场→选择1格钻石DA40（2,300金币）→免费配置1客位或1货位→装载真实订单→选上海并确认起飞→按时间抵达→领取首航奖励→完成培训。蒙版为当前真实按钮或弹窗留出可操作区域；机场详情仅为解锁按钮开孔，其他详情内容仍处于蒙版下；点击暗区只定位操作，不自动消费或推进经营。对话框只显示人物、当前经营步骤和右上角的“跳过引导”，不再放置存档设置、行动按钮或通用点击提示；全局顶部栏仍可操作。首步高亮未开放筛选和上海机场卡片，不高亮已选中的无效导航；暗区点击定位真实控件并显示高亮反馈，在购机弹窗中只聚焦输入，不代替确认。首航地图高亮上海点，视角和缩放变化时使用同一球面投影重新测量蒙版；暗区定位仅调整相机，顶栏只读，选点后再高亮检票起飞。首航培训结束后点击暗区结束教程。帮助中可重新开启；步骤由已提交的经营状态推导，刷新和取消购机不会跳步或额外发奖。购机弹窗关闭后丢弃未确认选配。半身像位于对话框左侧内部，允许头肩超出框顶；对话框桌面最大1040px，手机横屏保留左右边距。教程使用物理视口顶层弹出框，避免套用游戏逻辑画布的缩放与容器查询；窗口尺寸、滚动、图片加载及弹窗切换都会重新测量高亮区域。设置与竖屏提示优先于教程。

新公司的首航购置后余额3,600；北京至上海DA40满载单程成本96、运输收入326、运输净利230。到达只结算326运费，到账后余额3,830；领取首航600奖励后余额4,430。每次交付不再额外发放100–400金币航班奖励。所有金额通过真实经营流程验证，不凭教程弹窗结算。

教程中从机场列表或暗区定位进入机场详情，解锁首座目的地成功后都关闭详情并进入飞机商店，高亮真实购机按钮；此页面跳转不额外扣款或交付飞机，避免购机步骤被旧详情弹窗遮住。

## 运输经济

球面两机场的大圆距离为 `km`，航空版距离单位为：

```text
D(a, b) = floor(km(a, b) / 4)
```

普通旅客和货物订单的基础收入为：

```text
订单基础收入 = 数量 × (D(始发地, 最终目的地) + 50)
```

服务类型只决定订单表现和专业货舱条件，不改变金币倍率。自有生产物资运费为 0。

设编队等级为 `G`（0–6），进化等级为 `L`（0–20）：

```text
编队收益倍率 = 1 + 0.20 × G
进化收益倍率 = 1 + 0.015 × L
运输基础收入 = floor(该站交付订单基础收入总和 × 编队收益倍率 × 进化收益倍率)
部门附加收入 = floor((该站客运基础订单收入 × 客舱服务加成 + 该站货运基础订单收入 × 货运加成) / 100)
收入 = 运输基础收入 + 部门附加收入
```

客舱和货运加成各上限15%，仅来自有效部门员工，每个航段起飞时锁定并随航班保存；自产物资和空飞不计加成。部门效果、费用与容量详见 [公司组织](COMPANY-ORGANIZATION.md#航空公司部门扩充v18)。

没有满载奖励，也不检测是否满载。装载更多真实订单才增加基础收入。满级编队和进化合计为基础收入的 2.86 倍，避免原有 64 倍编队收益使后期价格失效。这些倍率与下述成本是航空版平衡参数，不是原作核验公式。

设实际航段距离单位之和为 `D路线`，强化后的重量、速度为 `W`、`S`，机型额定总容量为 `C`（不取已分配或已装载格数），航段数为 `K`：

```text
路线运行成本 = floor((D路线 × (0.24 × C + W × S / 600000)
                       + 12 × C × K) × (1 + 0.12 × G))
```

成本由随航程发生的运营支出和每次起飞的地面处理费组成。空机、未分配舱位的飞机仍按额定机体计成本；拆掉舱位不能规避成本。每多停一站增加该站处理费。整数系数计算后只取整一次；多段计划按累计成本差分分摊，航段扣款之和严格等于整条计划成本。订单收入始终按始发地到最终目的地计算，绕行不能增加收入。

平衡目标为基础机型普通满载航班约 65%–75% 利润率（短航线的固定票价部分会略抬高比例），低装载率与空飞可能亏损。此比例不计购机、机场、员工和改装投资，也不承诺随机候运池总能满载。完整价格、成长成本和测算边界见 [BALANCE.md](BALANCE.md)。

```text
净利润 = 各站实际交付收入之和 - 路线运行成本
```

净利润允许为负。报价是只读投影，只有成功起飞才扣除该航段成本；抵达只结算已锁定的交付收入。

## 客货、航班与经营时间

- 新订单代表 1 位旅客或 1 单位货物，具有固定始发地、最终目的地、位置和基础奖励。
- 装卸移动同一个订单对象，不复制订单。中转不付款；最终交付后删除订单并只记录一次统计。
- 已接受订单仍以不过期状态保留；在始发机场装载后卸回只恢复待装载，不标为中转。只有订单实际位于始发地以外的机场候运区时才显示中转；中转标签使用不透明浅金底、深色无描边文字，可用和不可用时均保持清晰，不随人物灰化。
- 固定机场星级与基础客源由真实单机场年客流决定；运营设施独立从Lv.1升级。基础候运目标为clamp(6,24,round(18×sqrt(年客流/70,742,712)))，设施按18／30／48相对18的倍率取整，推广另加6单，硬上限70。大型飞机的交付与航段准入按固定星级，公司业务仍按设施等级。每城静态配置3个基础方向，未开放时按大圆距离、机场ID顺延；开放基础方向共70%权重，其余30%，不存在另一类别时转移全部权重。仅对本次空余容量按最大余数法分配，余数同值按ID排序；客货生成序列2:1，专业货物仍需对应货舱。改选飞机、浏览或起飞不生成订单。全局订单上限7,160，文件校验上限8 MB。
- 自然客源补充每 120 秒检查所有开放客流的机场，未接受订单在生成 360 秒后过期；手动刷新只替换并补充所选机场的未接受订单，不补齐其他机场、不重置自然补充时间，已装机、已接受和中转订单保留。每日每机场前 10 次免费、之后每次 100 金币、最多 30 次的规则不变。
- 最多规划 12 段。计划保存路线总成本契约，后续航段按同一契约结算。
- 飞行起点与终点、出发和到达时间、成本、收入及载荷在起飞时锁定。
- 经营时间仅在已进入游戏且页面可见时按1:1推进；标题页、后台、关闭期间暂停航班、周转、补能、客源到期/补充、生产、合同、营业日、人才刷新和业务收入。到达、补能、生产等时间事件完成后先保存再更新画面；离开前保存当前进度，恢复可见时只重锚墙钟；启动、刷新、导入和备份恢复不补算离开期间的时间。删除8小时离线推进上限、收益报告及领奖/继续入口。墙钟回拨不倒退模拟时间；相同时间点不重复结算。断网游玩及PWA缓存保持可用。

## 公司组织与总经理

`career.employees` 是唯一员工名单。运输与总部组织包含 1 个总经理 NPC 槽位、飞行部与地勤部各 1 个经理槽位、最多 8 名飞行员和 4 名地勤专员，另设宣传、运行控制、机务工程、客舱服务、货运、人力资源、财务七部门（各1名经理、2名专员），运输与总部岗位合计最多 36 人，业务团队岗位另计。总经理使用公司岗位 `department: company`、`role: manager`；公司没有专员岗位。总经理和部门经理都不是基础手动经营的前提。

总经理从人才市场招募，录用即任命：费用为2,800金币，包含7天合同，初始专业2级、管理1级、潜力6–10；续付7天为1,000金币，培训和合同沿用现有人员规则。本期不支持通过内部晋升、降职或跨部门转任产生总经理。人才市场每批从总经理、九部门经理与专员共十九种岗位随机抽取候选，Lv.1每批3名，每升一级加1名，Lv.10起最多12名，允许同岗位重复，不保证所有岗位都有候选。

人才市场展示本批实际候选及“招聘部门”筛选；每张人物卡包含姓名、头像、岗位、已聘人数/岗位上限、潜力、特长、含7天合同的招募费用、每7天续约薪资和独立招募按钮，并注明不自动续约。卡片本身无选中态，不以整卡点击录用；岗位已满、缺少可分配资产或资金不足时，在卡内显示原因并禁用按钮。组织树职位空槽进入市场后筛选对应部门，有相应岗位候选时聚焦人物卡。没有候选的岗位组不显示，部门暂无候选和整批已录用显示不同空状态。公司等级、本批剩余人数和下批名额与倒计时一并显示。

所有招募入口均为录用即上岗，不再新增待分配人员：飞行员按机队顺序分配到首架未绑定员工且允许调岗的飞机（未飞行、无自动值勤与后续航段、未补能且地面周转已结束），同时开启该飞机的飞行员标记；地勤按已开放机场顺序分配到首座未绑定地勤的机场；七个总部职能部门专员录用即在岗；经理直接占用对应唯一岗位。岗位人数已满、没有可用飞机或机场时，界面禁用招募并显示原因，核心也在扣款和生成员工前拒绝；过期合同仍占据原岗位。人物卡显示招募后的自动分配目标，点击时由核心重新检查，录用、扣费、资产分配与移除被录用候选原子完成。新专员有本部门经理时自动直属该经理，否则由玩家直管；招募新专员不改变已有员工的分配和汇报关系，仍可手动调整；总经理任命时自动接管部门经理的既有规则保留。原存档中的未分配员工不自动迁移，存档格式为17。

人才市场每5分钟（300秒）整批更新，由核心模拟时间事件驱动，边界为全局经营时间 `n × 300` 秒。每批人数 `min(12, 当前公司等级 + 2)` 使用刷新时刻的等级；升级增加的名额在下一批生效。候选在周期内固定，录用后移除且不立即补位，不重置倒计时。打开市场、刷新网页、切换语言不重抽；标题、后台和关闭期间暂停名单与倒计时。刷新与航班等事件按时序推进；同刻先刷新后到达，恰好同刻到达带来的升级影响再下一批。更新使用独立随机种子及新编号，不修改员工；旧编号提交拒绝且不扣费。保存 `talent.batchLevel`，按本批等级校验0至本批名额个候选；规则并入尚未发布的v18，不迁移缺字段的中间开发存档。严格边界见 [人才市场与培养履历](COMPANY-TALENT.md)。

总经理无员工上级，不绑定飞机或机场；业务团队主管也可直属总经理，其产出规则见公司业务文档。部门经理可向总经理或玩家汇报；专员仍只能向本部门经理或玩家汇报。招募总经理时，现有部门经理自动成为其直属下属；之后新聘或内部晋升的部门经理同样自动直属总经理，玩家可再调整汇报关系。总经理除真实组织层级外，为直属业务团队增加管理效率；不增加航班收益、跨部门培训折扣或补能加成；既有部门经理对本部门专员的效果不变。组织树顶部显示真实总经理档案或可点击的招募空槽，不再将玩家画作总经理 NPC。相关规则见 [COMPANY-ORGANIZATION.md](COMPANY-ORGANIZATION.md) 与 [COMPANY-TALENT.md](COMPANY-TALENT.md)。

公司组织页移除“公司事务”和“公司纪事”入口及面板、员工头像上的事务提示标记；任务中心同步移除公司事务折叠区。人才市场招募、组织树、员工任职/培养/履历和机队负责飞行员跳转保留。事务与纪事的删除只涉及对应界面，核心记录规则和 `talent.deferred`、`talent.milestones` 存档字段及严格校验继续保留；当前存档仍为 `version: 18`，不因界面删除使有效进度失效。

## 存档与持久化

最多保留5个独立存档，每档有自己的自动保存、revision及上一份有效备份；满额时不覆盖任何进度，玩家可确认删除指定存档及其备份后再新建。打开标题只读取数据，不创建空存档或轮换备份。新游戏和标题页文件导入均先验证、原子创建成功再进入；游戏内导入仅替换当前槽位并保留该槽备份。切换前保存当前进度；返回标题暂停经营，载入时不补算间隔时间。每个标签页固定自己的存档ID，不随其他标签页改变“最近游玩”而写错公司；同档陈旧写入或删除后写入必须拒绝，不同档可独立保存。

多存档将数据库结构升级为2，增加存档目录与最近游玩记录。旧数据库的 main/backup 作为一个存档保留，记录内容和revision不改写；即使游戏格式不兼容也保留原记录并占用一个槽位，允许玩家显式删除。本次数值与币种调整后游戏格式为v18，不迁移旧游戏数据。

当前且唯一支持的保存格式为 `version: 18`，IndexedDB 结构版本为 2，两者独立管理。导入只接受字段集合、枚举、数值范围、引用关系、订单、人员、航班、能量、客货容量分配和路线成本契约全部有效的当前存档。旧 `version: 17`、`version: 16` 及所有其他版本文件拒绝导入；本版不提供自动迁移。升级前可导出旧版存档供旧版恢复，但新版本无法读取它；已有进度在本版会进入恢复界面。

版本不符、未知机型、未知机场、额外或缺失字段、非法数字及引用不一致都会拒绝。失败导入不得替换主存档或备份。保存时在同一事务中轮换上一份有效主存档到备份，并使用 revision 防止多标签页陈旧写入。

仓库不保留旧格式迁移代码、冻结目录、历史测试夹具或旧版设计规范。格式改变时直接更新当前设计、验证器和测试；不自动猜测或改写不兼容文件。

提交成功后记录平台返回的部署 ID 和 URL，确认公开项目目录及广场列表包含同一部署，再逐文件核对 SHA-256、执行线上新开局、存档导入导出、刷新离线及布局用例。平台提交或后置验收失败都必须报告阶段，不能把 HTTP 200 或静态上传成功当作上线验收。提交结果不确定时不自动撤回或回滚，避免覆盖较新版本；平台管理页提供人工恢复入口。上传失败尝试取消未提交的临时上传。旧 SSH 发布工作流已停用；在主站完成同名项目的托管迁移并允许发布前不重新启用。不得修改 riversoft.top 仓库来绕过这些约束。

游戏继续要求 IndexedDB、Service Worker 与离线运行；不接受 opaque sandbox 兼容入口。平台返回的地址必须属于平台 HTTPS 主域或其子域下当前项目路径，全部验收以该 URL 为基础。若主站选择不同 origin，已有浏览器存档无法自动跨域读取，需在旧地址导出后到新地址导入当前格式；旧线上文件不由游戏 CI 删除。原 GitHub Pages 自动发布继续停用。

未运行或失败的检查必须明确记录。功能分支通过 PR squash 合并；日常修改使用 riversoft.top 托管发布接口，不重复生成 ZIP。只有实际部署成功并验证目标端点后才能宣称上线。

自动交付只处理有仓库写权限人员登记的当前 head SHA 请求。可信 main 上的 `Automatic delivery` 由验证/生产完成事件触发，核对完整 `delivery-ready`、额外检查、最新 head/base/main 后 squash；不绕过分支保护。用 GITHUB_TOKEN 合并后显式 dispatch 生产，重复事件不重复发布，失败重跑须明确操作。结果写入同一条 PR 状态评论、Actions Summary 和 center JSON，失败附关键日志与原始任务链接。等待不调用模型或持续会话轮询；没有客户端回调时，不承诺主动送达聊天窗口。首次安装新工作流需要一次引导交付，后续由默认分支事件自动串联。

## center 构件存储与失败证据保留（2026-09-28）

所有新构件存到 `center` 的 `/var/lib/china-airlines-artifacts`，不再调用 GitHub Artifact 上传或下载。该目录由管理员预置、`git-runner` 所有且权限为0700，独立于会被 checkout 或任务清理的 workspace 与 `RUNNER_TEMP`。验证、UI 专项、生产与清理任务统一使用 `[self-hosted, Linux, X64, china-airlines-center]`；专用标签只赋给本仓库的 `VM-0-10-debian`，避免交接任务落到没有这些文件的其他机器。已有 GitHub 构件沿原过期日期保留，本次不删除其他仓库的任何构件。

成功验证不保存测试报告、截图、trace 或 JSON 构件，结果保留在工作流日志。仅验证失败时保存失败上下文与 `artifacts/`、`playwright-report/`、`test-results/` 中的已有证据，目录为 `reports/<run ID>-<attempt>-<分组>/`，各组独立且不可覆盖。文件复制完毕、写入身份与逐文件 SHA-256 清单后原子公布；符号链接、越界路径和 node_modules 拒绝，隐藏文件不收集。跨验证/生产及 UI 专项工作流保留最近一次已完成失败 attempt 的全部分组；后续成功不覆盖该记录，下一次失败证据成功保存且该运行结束后才删除更早证据。没有新证据则保留上一份，最长90天。失败判定发生在发布包保存之前，不能因证据保存错误重复保存；存储失败仍如实使任务失败。

独立 artifact-retention 工作流在 CI/生产运行结束后及每日串行清理，也允许手动触发。清理只执行默认分支受信任代码，使用 Actions read 权限查询真实运行及 attempt 状态，核对构件目录、工作流分组和完整性，不执行任何保存的产物。进行中或重新运行的任务受保护，删除前再次核对状态；未知、损坏或未完成的目录及已无法查询的运行留待人工核查，不删除工作流或日志。测试失败仍是失败，权限或清理失败要如实显示，不能改成验证成功。

生产发布包存到 `releases/<run ID>-<attempt>-<提交 SHA>/`，保留 `.tgz`、校验文件和身份清单。只有 main 的生产工作流可写入/读取；部署必须等待准备任务完成验证或确认可复用的完整验证，再校验运行编号、提交、包内容和 SHA-256。仅重跑部署时可复用同一运行/提交较早成功准备任务的包，重跑准备任务产生新的 attempt 目录；恢复选择不晚于当前 attempt 的最新包，损坏不得回退。包超过1天拒绝恢复，需重跑准备任务；完整生产运行成功后清理，失败运行的包满1天后清理，进行中不删。新失败分组为 `ci-full`、`production`、`deploy`，旧分片证据仍受保留规则管理。`delivery/` 保存小型验证回执及交付结果；回执2天后、结果90天后且运行已完成才清理，未知数据不删。这些记录不包含源码、依赖、密钥或用户存档。托管版本与恢复策略由 riversoft.top 管理，本仓库不操作服务器发布目录。
